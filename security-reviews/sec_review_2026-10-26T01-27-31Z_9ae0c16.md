## Findings

### Finding 1: The segment checker downloads the run from the mutable `main` branch, skips the anchor check, and labels the result with a pinned revision — `simple/fetch.sh:12`

- Severity: Medium
- Confidence: 0.8
- Category: integrity_verification_bypass
- Description: `checker_pod.sh` pins the release *code* to Hugging Face revision `96dc282a…` (`REV`). But the
  data the code checks is fetched by `fetch.sh` from `https://huggingface.co/datasets/$REPO/resolve/main/$f`. That
  includes `chain.jsonl`, `recipe.json`, the checkpoints and the prepared streams, all from the moving `main` branch.
  `verify_segment.sh` doesn't download `anchor.json`. `ovl.py verify` (`simple/ovl.py:526-534`) checks the chain
  head against `anchor.json` only if that file exists, and otherwise skips the check without a message. The
  printed result line then says `release 96dc282a`. So the line attests a revision that the checked data didn't
  come from, and the timestamped anchor, which binds the published record, is never consulted.
- Exploit Scenario: Anyone with write access to the dataset repo, or a compromised publisher, replaces
  `release/simple-run/chain.jsonl` and the checkpoints on `main` with a different but self-consistent run, for
  example one trained on altered data. Its `stream.json` hashes match its own streams. Independent checkers who
  deploy the one-click template recompute segments of the substituted run, get `MATCH`, and post
  `OVL check PASS … | release 96dc282a`. That reads as confirmation of the timestamped release. The only signal is
  the 12-character `final state` prefix in the line, and nothing compares it to the published value.
- Recommendation:
  1. In `fetch.sh`, download from `resolve/$REV` instead of `resolve/main`, with `REV` defaulting to the release
     revision and exported by `checker_pod.sh`.
  2. Fetch `anchor.json` in `verify_segment.sh`, and pass `--anchor "$RUN/anchor.json"` to `ovl.py verify`, so a
     missing anchor fails instead of skipping.
  3. Optionally, have `checker_pod.sh` compare the chain head with a pinned expected value
     (`934d681c99e5…`, the published final state) before it prints PASS.

## Notes

### Note 1: Signed checkpoints are unpickled with `weights_only=False` — `src/signing.py:132`

- Category: design-tradeoff
- Observation: `verified_torch_load` fully unpickles a checkpoint after its Ed25519 signature verifies against
  `keys/ovl_ed25519.pub`. Anyone holding the matching private key can produce a signed checkpoint that runs code
  on every checker that loads it.
- Rationale: This is the documented design (module docstring, `src/signing.py:1-24`). The signature is verified
  over the raw bytes before deserialization, the private key is git-ignored, and unsigned files fall back to
  `weights_only=True`. The released run (`simple/`) never uses this path: every `torch.load` in `simple/` passes
  `weights_only=True`. Keep the private key off shared machines.

### Note 2: The FreeTSA trust anchor is downloaded at check time — `simple/stamp.py:24`

- Category: accepted-risk
- Observation: `stamp.py --check` fetches FreeTSA's CA certificate and TSA certificate over HTTPS from
  freetsa.org each time it verifies, and uses them as the trust root. Someone who controls freetsa.org could serve
  a different root that validates forged FreeTSA timestamps.
- Rationale: The release is stamped by two independent authorities. The DigiCert timestamp is verified against
  the system CA store, and a forgery would need both. Pinning the SHA-256 of the two FreeTSA certificates in
  `stamp.py` would remove this dependency cheaply.

### Note 3: The verifier trusts the manifest's `weights` path — `src/verifier.py:99-105`

- Category: design-tradeoff
- Observation: `find_weights` joins `manifest["weights"]` to the model directory without rejecting absolute paths
  or `..`. A manifest could point the hash checks at a file outside the directory.
- Rationale: The manifest is covered by the Sigstore signature, and the verifier only gives GREEN with a pinned
  identity and issuer (#204). An attacker can't change `weights` without breaking the signature, and in
  `--allow-unsigned` mode every expected hash is self-declared anyway. Rejecting paths that leave the directory
  would still be a cheap hardening step.

## Limitations

**Standing limitations:**
- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed, or traced at runtime, so
  timing-dependent, load-dependent, or infrastructure-dependent issues cannot be confirmed here.
- Confidence scores are the reviewing model's own self-assessment, not a calibrated statistical probability.
- Absence of a reported finding does not mean the code is secure. Safety guardrails built into some models can
  cause a real vulnerability to be softened, generalized, or left out rather than reported in exploit-level
  detail, and training-data bias can make some vulnerability classes easier for a model to recognize than others.
  Treat this report as a floor on what a full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A vulnerability tied to a very recently disclosed
  CVE or library advisory may not be recognized as such.

**Review-specific limitations:**
- The frozen pipeline (`src/ovl_pipeline/`, `scripts/`), `Legacy/` and the July study modules were not reviewed.
  The data rebuild (`simple/rebuild_prep.sh`) runs `src/ovl_pipeline` code at a pinned revision, which was
  therefore not reviewed either.
- Third-party code (`model_signing`, `huggingface_hub`, PyTorch's `weights_only` unpickler) was taken as
  correct. The 18 dependency advisories reported by OpenSSF Scorecard were not traced to specific code paths.
